# 티켓

## 상태
todo → doing → review → merged → done

| 상태 | 누가 바꾸나 |
|---|---|
| todo | Product Owner(스토리), Software Architect(기술 티켓) |
| doing | 작업을 시작한 사람 (담당자에 자기 이름) |
| review | 작성자가 리뷰를 요청할 때 |
| merged | Release Manager가 병합했을 때 |
| done | QA Engineer가 PASS했을 때 (QA 생략 소변경은 Release Manager) |

## 스토리와 기술 티켓
- 스토리 티켓(Product Owner): 기능 ID 하나에 하나. 수락 기준 전체를 가진다.
- 기술 티켓(Software Architect): 스토리를 30~60분 단위로 쪼갠 것. 해당 수락 기준 ID만 가진다.
- QA는 기술 티켓마다 그 수락 기준을 확인하고, 하위 기술 티켓이 모두 done이면 스토리의 수락 기준 전체를 한 번 더 확인해 스토리를 done으로 바꾼다.

## tasks.json 동시 수정
여러 에이전트가 같은 파일을 고친다. 고치기 직전에 다시 읽고, 내 티켓 항목만 바꾸고, 바로 저장한다. 다른 티켓의 필드는 건드리지 않는다.

## 우선순위
| 등급 | 뜻 | 처리 |
|---|---|---|
| P0 | main 장애, 보안 Critical, 데이터 손실 | 하던 일을 멈추고 즉시 |
| P1 | Must 기능 | 리뷰·질의 다음 |
| P2 | Should 기능 | P1 다음 |
| P3 | Could, 정리 작업 | 여유 있을 때 |

## DoR (시작해도 되는 조건)
- [ ] 기능 ID와 수락 기준 ID가 있다
- [ ] 수정할 파일이나 폴더가 적혀 있고, 다른 doing 티켓과 겹치지 않는다
- [ ] 의존 티켓이 모두 done이다
- [ ] 필요한 디자인 규격, API 계약이 있다 (해당 시)
- [ ] 예상 변경이 400줄 이하다 (넘으면 기술 티켓을 만들 때 나눈다. 시작한 티켓은 더 쪼개지 않는다)

하나라도 빠지면 시작하지 않고 Delivery Manager에게 돌려보낸다.

## DoD (끝났다고 할 수 있는 조건)
- [ ] 수락 기준을 만족하는 코드와 테스트가 있다
- [ ] 린트, 빌드, **바뀐 파일 관련 테스트** 통과 (실행 명령과 결과 한 줄 첨부). 전체 `npm test`는 티켓마다 돌리지 않는다 (사용자 결정 2026-11-10, god 8e44ae)
- [ ] Code Reviewer 승인, 대기 점검 통과
- [ ] main에 병합 후 빌드, 바뀐 파일 관련 테스트 통과
- [ ] QA Engineer PASS (수락 기준 인용, 증거 첨부)
- [ ] 영향받는 문서 갱신 (계약, README 등)

DoD를 만족하지 못한 티켓은 done이 아니며 릴리스에 넣지 않는다.

## WIP 제한
- 동시에 doing인 구현 티켓은 최대 3개.
- 한 사람은 한 번에 티켓 하나.
- 끝나면 Delivery Manager의 배정을 기다리지 않고, 의존이 풀린 자기 역할 todo를 하나 가져간다. 단, doing인 구현 티켓이 이미 3개면 기다린다.

## 티켓 양식
```
제목: [F-03] 로그인 폼 서버 검증
기능 ID: F-03 / 수락 기준: AC-03-1, AC-03-2
담당 역할: Backend Developer
수정할 파일: src/server/auth/*
의존: NWS-10
예상 크기: 150줄
메모: (상태가 바뀔 때마다 한 줄)
```

## 한 티켓 = 한 브랜치 (사용자 결정 2026-11-10, god 8e44ae)
- 티켓 하나는 브랜치 하나, 리뷰 한 번, 병합 한 번으로 끝낸다. `feat/mpr-29a`·`29b`처럼 한 티켓을 여러 브랜치로 나누지 않는다.
- 리뷰 지적은 같은 브랜치에서 고쳐 같은 리뷰에 다시 올린다. 후속 티켓을 새로 만들지 않는다(리뷰 범위 밖의 새 결함·요구는 예외).
- 이미 쪼개진 채 남은 티켓·브랜치는 묶어서 한 번에 리뷰·병합한다.
